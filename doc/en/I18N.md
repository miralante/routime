# I18N.md — Routime multilingual architecture

> 🌐 **Other languages:** [Español](../es/I18N.md)

Technical reference of the internationalization system (`App.i18n`) and the
step-by-step recipe to add a new language. Read alongside
`doc/en/technical.md` §3.3 and §6 (technical integration) and `doc/en/SPEC.md`
§3–§4 (product and accessibility rules, which apply **in every language**).

**Current state**: Spanish (`es`, default) and English (`en`). The system is
designed for more than two languages, but it still has a few `es`/`en` binary
spots (number format, time expressions, the landing selector) that need to be
generalized when adding a third one — see §4.

The hidden routes (`settings/`, `about/`, `team/`, see `technical.md`
§8) follow the same multi-file pattern described here, not a special case.

**Language policy**:

- **User interface (UI)**: multilingual — every text visible to the end user
  exists in every supported language (`es`, `en`…).
- **Technical code**: **always in English** — variable, function and JS-object
  names, and **crucially the keys in `strings.<locale>.js`** must be in
  English. The values of those keys are the translatable UI text, but the
  key itself is code, so it is in English.

  ```js
  // ✅ Correct — English key, values in the file's language
  // tools/pairs/strings.es.js
  App.i18n.register({
    levelTitle: 'Elige el nivel', cardFaceDown: 'Carta boca abajo'
  }, 'es');
  // tools/pairs/strings.en.js
  App.i18n.register({
    levelTitle: 'Choose a level', cardFaceDown: 'Card face down'
  }, 'en');
  ```

  This split keeps `App.i18n.t('levelTitle')` readable in the source code,
  regardless of the active language.

## 0. Multi-file system (recent change)

Since v4, texts for each activity/landing are split **by language** in separate
files, instead of a single `strings.js` with `{es: {...}, en: {...}}`.

### Structure

```
site/strings.es.js    ← Spanish only (registers in locale 'es')
site/strings.en.js    ← English only (registers in locale 'en')

tools/pairs/strings.es.js    ← Spanish for the Pairs activity
tools/pairs/strings.en.js    ← English for the Pairs activity
... (same pattern for every activity)
```

### Advantages over the monolithic file

- **Only the active language is loaded**: before, both languages were sent to
  the end user (double download). Now only the locale's files are downloaded.
- **Independent maintenance**: a translator only edits the file of the language
  they know — they do not see the other language mixed in.
- **Cleaner diffs**: an English translation change shows only the English lines
  that changed, not the whole file.
- **Scalability**: adding a language is just creating `strings.<locale>.js` per
  activity, without touching the other languages.
- **Better caching**: the browser caches per language; switching language
  reloads from cache without re-downloading both.

### `strings.<locale>.js` pattern

```js
/* ============================================================
   Routime — Pairs texts (EN)
   Per-language file. Conditionally loaded from index.html
   according to App.i18n.locale().
   ============================================================ */
(function () {
  'use strict';

  App.i18n.register({
    title: '🃏 Pairs',
    instruction: 'Find the two matching cards. Touch a card to see it.',
    // ... rest of keys EN
  }, 'en');
})();
```

The second argument of `register(dict, locale)` indicates **which language** to
register. `App.i18n.js` stores it in `DICT[locale]` and keeps the fallback to
Spanish when a key is missing.

## 1. Pieces of the system

```
assets/js/i18n.js          # Core: App.i18n (detection, persistence, t/pick/apply)
site/strings.es.js        # Landing texts (ES)
site/strings.en.js        # Landing texts (EN)
site/index.html           # Language selector (2 fixed buttons) + conditional load
tools/<slug>/strings.es.js  # Activity texts (ES)
tools/<slug>/strings.en.js  # Activity texts (EN)
tools/<slug>/data.js       # Data: some indexed by language, some shared
tools/<slug>/app.js        # Uses App.i18n.t()/.pick()/.locale() to read/generate text
tools/<slug>/index.html    # Conditionally loads strings.<locale>.js per App.i18n.locale()
```

### 1.1 `assets/js/i18n.js` — core

```js
var SOPORTADOS = ['es', 'en'];   // activatable languages
var POR_DEFECTO = 'es';          // fallback when a key is missing or the detected language is not supported
```

- **Detection** (`detectar()`): walks through `navigator.languages` and takes
  the 2-letter prefix of the first one in `SOPORTADOS`. If none matches, it
  uses `POR_DEFECTO`.
- **Persistence** (`locale()` / `setLocale()`): `localStorage['routime:locale']`.
  A saved and supported value wins over detection. `setLocale()` saves and
  **reloads the page** (there is no hot re-render).
- **`register(dict)`**: legacy form `{es:{...}, en:{...}}`, kept for back-compat.
- **`register(dict, locale)`**: new multi-file form, registers in the given
  locale. Both locale files load synchronously from `index.html` (no
  `document.write`) so they are registered before `data.js` and `app.js`:
  ```html
  <script src="../../assets/js/utils.js"></script>
  <script src="../../assets/js/i18n.js"></script>
  <script src="../../assets/js/tts.js"></script>
  <script src="../../assets/js/storage.js"></script>
  <script src="../../assets/js/feedback.js"></script>
  <script src="strings.es.js"></script>
  <script src="strings.en.js"></script>
  <script src="data.js"></script>
  <script src="app.js"></script>
  ```
  `document.write` is **not** used: Chrome and Firefox process scripts
  injected via `document.write` asynchronously, so they would load *after*
  `data.js`/`app.js` and `App.i18n.t()` would return literal keys during the
  initial render. `tts.js` and `feedback.js` only depend on the locale and
  on the common keys already defined in `i18n.js`.

- **`t(key)`**: looks up `key` (with dots, e.g. `'nivel.c1'` or `'core.back'`) in
  the active language. If missing, falls back to `POR_DEFECTO` (Spanish). If
  still missing, it returns the `key` itself (so broken keys are visible on
  screen). If the value is an array, it joins it with `', '` (meant for
  debugging, not for the UI).
- **`pick(key)`**: like `t`, but for keys whose value is an **array** of
  variants (e.g. `feedback.success`) — returns a random element. Used by
  `feedback.js` for the success/encouragement messages.
- **`apply(root)`**: applies `data-i18n` (→ `textContent`) and `data-i18n-aria`
  (→ `aria-label`) to every DOM node under `root` (default `document`). Runs
  on `DOMContentLoaded`. It also sets `document.documentElement.lang` and, if
  `<html>` has `data-i18n-title="key"`, sets `document.title = t(key) + ' | Routime'`.
- **`lang()`**: `'es' → 'es-ES'`, anything else → `'en-US'` (binary today — see
  §4). Used by `App.tts.speak()` to pick the speechSynthesis voice.

### 1.2 Common keys (`core.*`, `feedback.*`)

Defined once in `i18n.js`; **do not redefine** them in each tool's
`strings.<locale>.js`. All subkeys are in English (technical code):

| Key | ES | EN |
|---|---|---|
| `core.back` | ← Volver | ← Back |
| `core.backToMenu` | Volver al menú | Back to menu |
| `core.playAgain` | Jugar otra vez | Play again |
| `core.next` | Siguiente → | Next → |
| `core.listen` | 🔊 Escuchar | 🔊 Listen |
| `core.listenInstructions` | Escuchar las instrucciones | Listen to the instructions |
| `core.listenText` | Escuchar el texto | Listen to the text |
| `core.loading` | Cargando… | Loading… |
| `core.roundComplete` | ¡Ronda completada! | Round complete! |
| `feedback.success` (array) | ¡Muy bien! / ¡Genial! / … | Well done! / Great! / … |
| `feedback.encourage` (array) | Casi. ¡Inténtalo otra vez! / … | Almost. Try again! / … |

### 1.3 `strings.<locale>.js` per tool

Pattern (see `tools/pairs/strings.es.js` as the gold reference):

```js
/* tools/pairs/strings.es.js */
(function () {
  'use strict';
  App.i18n.register({
    title: 'Parejas',
    instruction: 'Busca las dos cartas iguales. Toca una carta para verla.',
    pairsPerLevel: '{n} parejas',
    // ... rest of ES keys
  }, 'es');
})();
```

```js
/* tools/pairs/strings.en.js */
(function () {
  'use strict';
  App.i18n.register({
    title: 'Pairs',
    instruction: 'Find the two matching cards. Touch a card to see it.',
    pairsPerLevel: '{n} pairs',
    // ... rest of EN keys
  }, 'en');
})();
```

**Important**: the keys (`title`, `instruction`, `pairsPerLevel`) are technical
code and always in English, regardless of the UI language. The values are the
user-facing translatable text.

- There must always be a `title` key (used by `data-i18n-title` for the
  `<title>`).
- Keys **must match exactly** between `strings.es.js` and `strings.en.js`
  (verified by `scripts/check.js` §4).
- Brace placeholders (`'{n} times'`) are replaced manually in `app.js` with
  `.replace('{n}', value)` — **there is no interpolation engine**; if a key
  uses the same placeholder twice, use `.replace(/\{n\}/g, value)`.
- Nested objects work as namespaces: `nivel: { c1: '...', c2: '...' }` is
  read with `t('nivel.c1')`.
- **Never** use an array when you need positional indexing (`t()` would join
  the array with commas). For position-indexed tables, use an object with text
  keys: `{0: '', 1: 'miles', 2: 'millones'}` and read with `t('grupoEtq.' + i)`.

### 1.4 Where the text lives: three `data.js` patterns

1. **Data indexed by id, text in `strings.<locale>.js`** (recommended when most
   fields are structural: coordinates, colors, level ids…). Example:
   `tools/coloring/data.js` stores `{ id: 'casa', picto: '🏠', zonas: [...] }`
   and `app.js` looks up the name with `App.i18n.t('dibujo.' + d.id)`.
2. **`DATA` fully duplicated per language** (`{ es: [...], en: [...] }`) when
   almost every field is text or the content differs deeply between languages
   (readings of large numbers). Example: `tools/idioms/data.js`, where
   `DATA` itself is `{ es: [...], en: [...] }`. Accessed as
   `DATA[App.i18n.locale()]` (or `DATA.<field>[App.i18n.locale()]` when
   only some fields are duplicated per language).
3. **Shared, language-independent data** when the value really does not depend on
   the language: amounts in cents (`DATA.llegaUno`/`DATA.cambio` in `numeros`).

### 1.5 HTML: `data-i18n*` attributes

```html
<html lang="es" data-i18n-title="title">
...
<h1 data-i18n="title">Parejas</h1>
<button data-i18n-aria="core.listenInstructions" aria-label="Escuchar las instrucciones">🔊</button>
```

The Spanish text/`aria-label` is left as the HTML default content (so the page
still makes sense if `i18n.js` fails to load) and `apply()` overwrites it on
start. Attributes that `apply()` **does not** cover (set manually in `app.js` on
start): `placeholder` on `<textarea>`/`<input>`.

### 1.6 Mandatory script load order

```html
<script src="../../assets/js/utils.js"></script>
<script src="../../assets/js/i18n.js"></script>
<script src="../../assets/js/tts.js"></script>
<script src="../../assets/js/storage.js"></script>
<script src="../../assets/js/feedback.js"></script>
<!-- Both locale files load synchronously, no document.write -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

`i18n.js` loads before `tts.js`/`feedback.js` (both read the active language).
Both `strings.<locale>.js` files load synchronously **before** `data.js` and
`app.js`, so `App.i18n.register` has already populated the dictionary by the
time any UI code calls `App.i18n.t()`. `document.write` is intentionally
**not** used: see [`technical.md` §6.2](../en/technical.md#62-conditional-load-in-indexhtml)
for why the old `document.write` pattern caused literal keys to leak into the
DOM in modern browsers.

### 1.7 Language selector (landing)

`site/index.html` has **two fixed buttons** (not generated from `SOPORTADOS`):

```html
<div class="idioma-selector" role="group" aria-label="Elegir idioma">
  <button id="btnIdiomaEs" data-locale="es" aria-pressed="false">🇪🇸 Español</button>
  <button id="btnIdiomaEn" data-locale="en" aria-pressed="false">🇬🇧 English</button>
</div>
```

with its own JS (`pintarSelectorIdioma()`, click listeners → `App.i18n.setLocale(...)`)
in `site/index.html`. Adding a language means adding a third button by hand (§5).

## 2. Number, money and time format: NOT just translation

These three areas are the most delicate part of the system — translating the
word without touching the format produces a number or a time that reads wrong
or is outright false:

- **Thousand/decimal separators**: Spanish uses `.` for thousands and `,` for
  decimals (`1.234,50`); English the other way around (`1,234.50`). See
  `assets/js/dinero.js` (line with `App.i18n.locale() === 'en' ? '.' : ','`) for
  a live example — any activity that formats a number or an amount needs the
  same per-locale branch, not a literal translation of the separator.
- **Number scale**: Spanish uses the long scale (1 000 000 000 = "mil millones",
  1 000 000 000 000 = "un billón"); English uses the short scale (10⁹ = "one billion",
  10¹² = "one trillion"). Translating "billón" as "billion" gives a number
  **one thousand times smaller** than the intended one. An activity that reads
  large numbers aloud needs genuinely different `es`/`en` word-list arrays in
  `data.js` (not a translated copy of the same list) plus locale-specific
  group labels in `strings.<locale>.js` (Spanish needs `'miles de
  millones'`/`'billones'` patches every 3 digits; English has one word per
  group: `thousand/million/billion/trillion`). Calculia's `tools/numbers/`
  (now a separate app of the suite) is a worked example of this pattern
  if you need to port it back.
- **Times**: "y cuarto" / "menos cuarto" / "y media" are not "and a quarter" /
  "less a quarter" in natural English — they are "quarter past" / "quarter to"
  / "half past". Any activity that reads a clock aloud needs a small
  `es`/`en` phrase table for these fixed expressions, not a word-for-word
  translation. Calculia's `tools/clock/` (now a separate app of the
  suite) is a worked example of this pattern if you need to port it back.

**General rule**: before translating word-for-word a text with a number, a date,
a time or a currency, check how a native speaker would actually say it. If
necessary, the template can have a different sentence structure per language
(see `precioConCentimos`, with `'{euros} y {c} céntimos'` in Spanish vs.
`'{euros} and {c} cents'` in English — same order here, but do not assume it).

## 3. Cultural content (sayings, jokes, riddles, names): do NOT translate literally

A rule as strict as §2, but for text instead of numbers: **a saying, a joke or a
riddle translated word-for-word from Spanish stops working in English** — the
joke is no longer funny, the saying does not exist as such, the riddle loses
the rhyme or the double meaning it relied on. The version in each language has
to be content **native to that language**, with the same difficulty and
pedagogical intent as the original, not a translation of it.

- **`tools/idioms/`**: the English sayings are real English idioms
  ("Break the ice", "Piece of cake", "Once in a blue moon"), not the
  translation of "A quien madruga, Dios le ayuda".
- **`tools/comedy-club/`**: the English jokes are wordplay that works in
  English ("Why did the bicycle fall over? Because it was two-tired.").
- **`tools/sentence/`**: the character names are English given names
  (`Emma`, `Jack`, `Grace`, `Grandma`), not the Spanish ones.
- **`tools/categories/`, `tools/vocabulary/`, `tools/whats-missing/`, etc.** (everyday
  vocabulary of objects): a direct word-for-word translation is fine here
  (`Perro` → `Dog`).

## 4. `es`/`en` binary spots (to be generalized when adding a language)

Reference grep: `grep -rn "locale() === 'en'" assets/ tools/`.

| File:line | What it does | What to change for a 3rd language |
|---|---|---|
| `assets/js/i18n.js:17` (`SOPORTADOS`) | `var SOPORTADOS = ['es', 'en'];` | Add the language code: `['es', 'en', 'fr']` |
| `assets/js/i18n.js:87` (`lang()`) | `return locale() === 'en' ? 'en-US' : 'es-ES';` | Replace with a map `{es:'es-ES', en:'en-US', fr:'fr-FR'}` and a fallback |
| `assets/js/dinero.js:83` (decimal separator) | `App.i18n.locale() === 'en' ? '.' : ','` | Per-language map |
| `site/index.html` (buttons) + `pintarSelectorIdioma()` | 2 fixed buttons | Add a third `<button>` + entry in `pintarSelectorIdioma()` + listener |

## 5. Recipe: adding a new language (example: French, `fr`)

Follow these steps in order. Every step is mechanical except step 4 (content)
and step 5 (numbers/times).

### Step 1 — Register the language in the core

In `assets/js/i18n.js`:

```js
var SOPORTADOS = ['es', 'en', 'fr'];
```

Add `fr` to the `core`/`feedback` dictionary:

```js
fr: {
  core: {
    back: '← Retour', backToMenu: 'Retour au menu', playAgain: 'Rejouer',
    next: 'Suivant →', listen: '🔊 Écouter',
    listenInstructions: 'Écouter les instructions', listenText: 'Écouter le texte',
    loading: 'Chargement…', roundComplete: 'Manche terminée !'
  },
  feedback: {
    success: ['Bravo !', 'Génial !', "Tu l'as fait !"],
    encourage: ['Presque. Essaie encore !', 'Pas grave. Encore une fois !']
  }
}
```

Generalize `lang()` (binary today, see §4):

```js
var BCP47 = { es: 'es-ES', en: 'en-US', fr: 'fr-FR' };
function lang() { return BCP47[locale()] || BCP47[POR_DEFECTO]; }
```

### Step 2 — Language selector on the landing

In `site/index.html`, add a third button inside `.idioma-selector`:

```html
<button type="button" class="btn-idioma" id="btnIdiomaFr" data-locale="fr" aria-pressed="false">🇫🇷 Français</button>
```

and in the `<script>` of the same page: add its line in `pintarSelectorIdioma()`
and its `addEventListener('click', () => App.i18n.setLocale('fr'))`.

### Step 3 — Landing: `site/strings.fr.js`

Create the `strings.fr.js` file with the same keys as `strings.es.js` /
`strings.en.js`:

```js
(function () {
  'use strict';
  App.i18n.register({
    title: 'Routime',
    saludo: '...',
    // ... rest of keys translated to French
  }, 'fr');
})();
```

### Step 4 — Create `strings.fr.js` per activity (66 files)

For each `tools/<slug>/strings.es.js` and `tools/<slug>/strings.en.js`, create the
equivalent `strings.fr.js` with the **same keys** (same names, same nested
structure). The parity validator in step 7 will check it.

This is the most tedious step. Consider automating it in the future with a
generation script based on `strings.es.js`.

### Step 5 — French-specific format (numbers, times, money)

Word-for-word translation is not enough (see §2):

- **Numbers**: French also uses the long scale like Spanish (10⁹ = "milliard").
  Double-check `DATA.lecturas`.
- **Separators**: French uses a thin space for thousands and `,` for decimals.
- **Times**: "trois heures et quart" / "moins le quart" / "et demie" — write the
  keys thinking how a native speaker would actually say it.

### Step 6 — Update `sw.js` and `scripts/check.js`

Bump `VERSION` in `sw.js` and add each activity's `strings.fr.js` to the
`ARCHIVOS` array. The `scripts/check.js` regex (check #3) accepts any locale
configured in `STRING_LOCALES`; just add `'fr'` at the start of that array.

### Step 7 — Verify key parity

`scripts/check.js` already validates that `strings.es.js`, `strings.en.js` (and
any other `strings.<locale>.js`) have **exactly the same keys**. When you add
`fr`, update `STRING_LOCALES` in `scripts/check.js` to include `'fr'`:

```js
var STRING_LOCALES = ['es', 'en', 'fr'];
```

Then run:

```bash
node scripts/check.js
```

If any key is missing in `fr`, `check.js` will list it with detail ("only in es",
"only in en").

### Step 8 — Functional verification

- Landing: the third button changes the whole site and persists in
  `localStorage['routime:locale']`.
- Each tool loads without console errors in the new language.
- `numeros` and `reloj` in particular: read a few questions aloud and check
  that the number/time is correct.

## 6. What NOT to do

- Do not accept a machine translation of numbers, dates, times or money without
  checking the real convention of the target language (§2 and step 5).
- Do not leave a key without its equivalent in every supported language — the
  Spanish fallback hides the gap instead of failing loudly.
- Do not use arrays in `strings.<locale>.js` for data indexed by position/number
  (`t()` flattens them with `join(', ')`); use an object with text keys
  (`{0:'', 1:'...'}`).
- Do not add a new language without first generalizing the `es`/`en` binary
  spots of §4 — otherwise the new language will silently inherit the English
  (or Spanish) behavior for number/time format.
- Do not literally translate sayings, jokes, riddles or any text that depends
  on wordplay, rhyme or cultural reference — write native content for the
  target language with the same difficulty and intent (§3).
- **Do not delete the monolithic `strings.js` files without updating
  `sw.js`**: the service worker caches the files listed in `ARCHIVOS`. After
  the multi-file refactor, `strings.<locale>.js` replace `strings.js`
  (bump `VERSION` to force a redownload).

## 7. Historical summary

- **v3.x (legacy)**: a single `strings.js` per activity with
  `{es: {...}, en: {...}}`. Simple, but it mixed languages in one file and
  downloaded both to the client.
- **v4+**: multi-file system with `strings.<locale>.js`, conditional load
  from `index.html` via synchronous `document.write`. Backward-compatible
  with the legacy `register(dict)` signature for smooth migrations.
- **Migration**: running `node scripts/refactor-i18n.js` from the repo root
  automatically converts every `strings.js` to `strings.es.js` +
  `strings.en.js`, updates the corresponding `index.html` and deletes the
  monolithic file. Backed by `--dry-run` to simulate without touching files.
