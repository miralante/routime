# I18N.md — Arquitectura multiidioma de Routime

> 🌐 **Otros idiomas:** [English](../en/I18N.md)

Referencia técnica del sistema de internacionalización (`App.i18n`) y receta paso a
paso para añadir un idioma nuevo. Leer junto a `tecnico.md` §3.3 y §6
(integración técnica) y `SPEC.md` §3–§4 (reglas de producto y accesibilidad,
que aplican **en todos los idiomas**).

**Estado actual**: español (`es`, por defecto) e inglés (`en`). El sistema está
diseñado para más de dos idiomas, pero hoy tiene varios puntos con lógica binaria
`es`/`en` (formato de números, expresiones horarias, selector de la landing) que
hay que generalizar al añadir un tercero — ver §4.

Las rutas ocultas (`settings/`, `about/`, `team/`, ver `tecnico.md` §8)
siguen el mismo patrón multi-archivo descrito aquí, no un caso especial.

**Política de idioma**:

- **Interfaz de usuario (UI)**: multiidioma — todos los textos visibles para el
  usuario final existen en cada idioma soportado (`es`, `en`…).
- **Código técnico**: **siempre en inglés** — nombres de variables, funciones,
  objetos JavaScript y, **crucialmente, las claves de `strings.<locale>.js`** deben ser
  en inglés. Los valores de las claves son el texto traducible (UI), pero la
  clave misma es código técnico y por tanto va en inglés.

  ```js
  // ✅ Correcto — clave en inglés, valores en el idioma del archivo
  // tools/pairs/strings.es.js
  App.i18n.register({
    levelTitle: 'Elige el nivel', cardFaceDown: 'Carta boca abajo'
  }, 'es');
  // tools/pairs/strings.en.js
  App.i18n.register({
    levelTitle: 'Choose a level', cardFaceDown: 'Card face down'
  }, 'en');
  ```

  Esta distinción permite que `App.i18n.t('levelTitle')` sea legible en el código
  fuente, independientemente del idioma activo.

---

## 0. Sistema multi-archivo (cambio reciente)

Desde v4, los textos de cada actividad/landing se dividen **por idioma** en archivos
separados, en lugar de un único `strings.js` con `{es: {...}, en: {...}}`.

### Estructura

```
site/strings.es.js    ← solo español (registra en el locale 'es')
site/strings.en.js    ← solo inglés (registra en el locale 'en')

tools/pairs/strings.es.js    ← solo español de la actividad Parejas
tools/pairs/strings.en.js    ← solo inglés de la actividad Parejas
... (igual para todas las actividades)
```

### Ventajas sobre el monolítico

- **Carga solo el idioma activo**: antes se enviaban ambos idiomas a la persona
  usuaria (descarga doble). Ahora se envía solo el del locale elegido.
- **Mantenimiento independiente**: un traductor solo edita el archivo del idioma
  que conoce — no ve el otro idioma mezclado.
- **Diffs limpios**: un cambio en la traducción inglesa muestra solo los textos
  cambiados en inglés, no todo el archivo.
- **Escalabilidad**: añadir un idioma es solo crear `strings.<locale>.js` por
  actividad, sin tocar los otros idiomas.
- **Mejor caché**: el navegador cachea por idioma; cambiar de idioma recarga
  desde caché sin re-descargar ambos.

### Patrón de `strings.<locale>.js`

```js
/* ============================================================
   Routime — Textos de Parejas (ES)
   Archivo específico del idioma. Se carga condicionalmente
   desde index.html según App.i18n.locale().
   ============================================================ */
(function () {
  'use strict';

  App.i18n.register({
    title: '🃏 Parejas',
    instruccion: 'Busca las dos cartas iguales. Toca una carta para verla.',
    // ... resto de claves ES
  }, 'es');
})();
```

El segundo argumento de `register(dict, locale)` indica **a qué idioma** se registra.
`App.i18n.js` se encarga de almacenarlo en `DICT[locale]` y mantener el fallback a
español cuando una clave falta.

## 1. Piezas del sistema

```
assets/js/i18n.js          # Núcleo: App.i18n (detección, persistencia, t/pick/apply)
site/strings.es.js        # Textos ES de la landing
site/strings.en.js        # Textos EN de la landing
site/index.html           # Selector de idioma (2 botones fijos) + carga condicional
tools/<slug>/strings.es.js  # Textos ES de la actividad
tools/<slug>/strings.en.js  # Textos EN de la actividad
tools/<slug>/data.js       # Datos: algunos indexados por idioma, otros compartidos
tools/<slug>/app.js        # Usa App.i18n.t()/.pick()/.locale() para leer/generar texto
tools/<slug>/index.html    # Carga condicional de strings.<locale>.js según App.i18n.locale()
```

### 1.1 `assets/js/i18n.js` — núcleo

```js
var SOPORTADOS = ['es', 'en'];   // idiomas activables
var POR_DEFECTO = 'es';          // fallback si falta una clave o el idioma detectado no está soportado
```

- **Detección** (`detectar()`): recorre `navigator.languages`, se queda con el
  prefijo de 2 letras del primero que esté en `SOPORTADOS`. Si ninguno coincide,
  usa `POR_DEFECTO`.
- **Persistencia** (`locale()` / `setLocale()`): `localStorage['routime:locale']`.
  Si hay un valor guardado y soportado, gana sobre la detección. `setLocale()`
  guarda y **recarga la página** (no hay re-render en caliente).
- **`register(dict)`**: forma legacy `{es:{...}, en:{...}}`, retrocompatible.
- **`register(dict, locale)`**: forma nueva multi-archivo, registra solo en
  el locale pasado. Ambos archivos de locale se cargan de forma síncrona
  desde `index.html` (sin `document.write`), así que se registran antes de
  `data.js` y `app.js`:
  ```html
  <script src="../../assets/js/utils.js"></script>
  <script src="../../assets/js/i18n.js"></script>
  <script src="../../assets/js/tts.js"></script>
  <script src="../../assets/js/storage.js"></script>
  <script src="../../assets/js/feedback.js"></script>
  <script src="strings.es.js"></script>
  <script src="strings.en.js"></script>
  <script src="data.js"></script>
  <script src="app.js"></script>
  ```
  No se usa `document.write`: Chrome y Firefox procesan los `<script>`
  inyectados por `document.write` de forma asíncrona, por lo que cargarían
  *después* de `data.js`/`app.js` y `App.i18n.t()` devolvería la clave literal
  durante el renderizado inicial. `tts.js` y `feedback.js` solo dependen del
  locale y de las claves comunes ya definidas en `i18n.js`.

- **`t(key)`**: busca `key` (con puntos, p. ej. `'nivel.c1'` o `'core.back'`) en el
  idioma activo. Si no está, cae a `POR_DEFECTO` (español). Si tampoco está,
  devuelve la propia `key` (para detectar claves rotas a simple vista en pantalla).
  Si el valor es un array, lo une con `', '` (pensado para depurar, no para UI).
- **`pick(key)`**: como `t`, pero para claves que son un **array** de variantes
  (p. ej. `feedback.success`) — devuelve una al azar. Usado por `feedback.js` para
  los mensajes de ánimo/acierto.
- **`apply(root)`**: aplica `data-i18n` (→ `textContent`) y `data-i18n-aria`
  (→ `aria-label`) a todo el DOM bajo `root` (por defecto `document`). Se ejecuta
  sola en `DOMContentLoaded`. También pone `document.documentElement.lang` y, si
  `<html>` tiene `data-i18n-title="clave"`, fija `document.title = t(clave) + ' | Routime'`.
- **`lang()`**: `'es' → 'es-ES'`, cualquier otro → `'en-US'` (hoy binario — ver §4).
  Lo usa `App.tts.speak()` para elegir la voz de `speechSynthesis`.

### 1.2 Claves comunes (`core.*`, `feedback.*`)

Definidas una vez en `i18n.js`, **no redefinir** en el `strings.<locale>.js` de cada
herramienta. Todas las subclaves van en inglés (código técnico):

| Clave | ES | EN |
|---|---|---|
| `core.back` | ← Volver | ← Back |
| `core.backToMenu` | Volver al menú | Back to menu |
| `core.playAgain` | Jugar otra vez | Play again |
| `core.next` | Siguiente → | Next → |
| `core.listen` | 🔊 Escuchar | 🔊 Listen |
| `core.listenInstructions` | Escuchar las instrucciones | Listen to the instructions |
| `core.listenText` | Escuchar el texto | Listen to the text |
| `core.loading` | Cargando… | Loading… |
| `core.roundComplete` | ¡Ronda completada! | Round complete! |
| `feedback.success` (array) | ¡Muy bien! / ¡Genial! / … | Well done! / Great! / … |
| `feedback.encourage` (array) | Casi. ¡Inténtalo otra vez! / … | Almost. Try again! / … |

### 1.3 `strings.<locale>.js` de cada herramienta

Patrón (ver `tools/pairs/strings.es.js` como referencia de oro):

```js
/* tools/pairs/strings.es.js */
(function () {
  'use strict';
  App.i18n.register({
    title: '🃏 Parejas',
    instruction: 'Busca las dos cartas iguales. Toca una carta para verla.',
    pairsPerLevel: '{n} parejas',
    // ... resto de claves ES
  }, 'es');
})();
```

```js
/* tools/pairs/strings.en.js */
(function () {
  'use strict';
  App.i18n.register({
    title: '🃏 Pairs',
    instruction: 'Find the two matching cards. Touch a card to see it.',
    pairsPerLevel: '{n} pairs',
    // ... resto de claves EN
  }, 'en');
})();
```

**Importante**: las claves (`title`, `instruction`, `pairsPerLevel`) son código
técnico y van siempre en inglés, independientemente del idioma de la UI. Los
valores son el texto traducible para el usuario.

- Debe existir siempre la clave `title` (la usa `data-i18n-title` para el `<title>`).
- Las **claves deben coincidir exactamente** entre `strings.es.js` y `strings.en.js`
  (verificado por `scripts/check.js` §4).
- Placeholders con llaves (`'{n} veces'`) se sustituyen a mano en `app.js` con
  `.replace('{n}', valor)` — **no hay motor de interpolación**; si una clave tiene
  el mismo placeholder repetido dos veces, hay que usar `.replace(/\{n\}/g, valor)`.
- Objetos anidados funcionan como namespaces: `nivel: { c1: '...', c2: '...' }` se
  lee con `t('nivel.c1')`.
- **Nunca** un array cuando se necesita indexar por posición (`t()` uniría el array
  con comas). Para tablas indexadas por número usar un objeto con claves de texto:
  `{ 0: '', 1: 'miles', 2: 'millones' }` y leer con `t('grupoEtq.' + i)`.

### 1.4 Dónde vive el texto: tres patrones de `data.js`

1. **Datos indexados por id, texto en `strings.<locale>.js`** (recomendado cuando la mayoría
   de campos son estructurales: coordenadas, colores, ids de nivel…). Ejemplo:
   `tools/coloring/data.js` guarda `{ id: 'casa', picto: '🏠', zonas: [...] }` y
   `app.js` busca el nombre con `App.i18n.t('dibujo.' + d.id)`.
2. **`DATA` duplicado completo por idioma** (`{ es: [...], en: [...] }`) cuando casi
   todos los campos son texto o cambian de fondo entre idiomas (números de una
   lectura). Ejemplo: `tools/idioms/data.js`, donde `DATA` en sí es
   `{ es: [...], en: [...] }`. Se accede con `DATA[App.i18n.locale()]`
   (o `DATA.<campo>[App.i18n.locale()]` cuando solo algunos campos se
   duplican por idioma).
3. **Datos compartidos sin duplicar**, cuando de verdad no dependen del idioma:
   importes en céntimos (`DATA.llegaUno`/`DATA.cambio` en `numeros`).

### 1.5 HTML: atributos `data-i18n*`

```html
<html lang="es" data-i18n-title="title">
...
<h1 data-i18n="title">🃏 Parejas</h1>
<button data-i18n-aria="core.listenInstructions" aria-label="Escuchar las instrucciones">🔊</button>
```

El texto/`aria-label` español queda como contenido por defecto en el HTML (para que
la página tenga sentido incluso si `i18n.js` no cargase) y `apply()` lo sobrescribe
al arrancar. Atributos que `apply()` **no** cubre (hay que fijarlos a mano en
`app.js` al arrancar): `placeholder` de `<textarea>`/`<input>`.

### 1.6 Orden de carga de scripts (obligatorio)

```html
<script src="../../assets/js/utils.js"></script>
<script src="../../assets/js/i18n.js"></script>
<script src="../../assets/js/tts.js"></script>
<script src="../../assets/js/storage.js"></script>
<script src="../../assets/js/feedback.js"></script>
<!-- Ambos archivos de locale cargan de forma síncrona, sin document.write -->
<script src="strings.es.js"></script>
<script src="strings.en.js"></script>
<script src="data.js"></script>
<script src="app.js"></script>
```

`i18n.js` carga antes que `tts.js`/`feedback.js` (ambos leen el idioma activo).
Los dos archivos `strings.<locale>.js` cargan de forma síncrona **antes** de
`data.js` y `app.js`, así que `App.i18n.register` ya rellenó el diccionario
cuando cualquier código de UI llama a `App.i18n.t()`. `document.write` se
evita a propósito: véase [`tecnico.md` §6.2](../es/tecnico.md#62-carga-condicional-en-indexhtml)
para entender por qué el patrón antiguo con `document.write` provocaba que
las claves se filtraran al DOM como literales en los navegadores modernos.

### 1.7 Selector de idioma (landing)

`site/index.html` tiene **dos botones fijos** (no generados desde `SOPORTADOS`):

```html
<div class="idioma-selector" role="group" aria-label="Elegir idioma">
  <button id="btnIdiomaEs" data-locale="es" aria-pressed="false">🇪🇸 Español</button>
  <button id="btnIdiomaEn" data-locale="en" aria-pressed="false">🇬🇧 English</button>
</div>
```

con JS propio (`pintarSelectorIdioma()`, listeners de `click` → `App.i18n.setLocale(...)`)
en `site/index.html`. Añadir un idioma implica añadir un tercer botón a mano (§5).

## 2. Formato de números, dinero y horas: NO es solo traducción

Estos tres puntos son la parte más delicada del sistema — traducir la palabra sin
tocar el formato produce un número o una hora que se lee mal o directamente falso:

- **Separadores de miles/decimales**: español usa `.` para miles y `,` para
  decimales (`1.234,50`); inglés al revés (`1,234.50`). Ver
  `assets/js/dinero.js` (línea con `App.i18n.locale() === 'en' ? '.' : ','`)
  como ejemplo vivo — cualquier actividad que formatee un número o un importe
  necesita la misma bifurcación por idioma, no una traducción literal del
  separador.
- **Escala numérica**: el español usa escala larga (1 000 000 000 = "mil millones",
  1 000 000 000 000 = "un billón"); el inglés usa escala corta (10⁹ = "one billion",
  10¹² = "one trillion"). Traducir "billón" por "billion" da un número **mil veces
  menor** del que se quería decir. Una actividad que lea números grandes en voz
  alta necesita arrays `es`/`en` con palabras genuinamente distintas en
  `data.js` (no una copia traducida de la misma lista) más etiquetas de grupo
  específicas por idioma en `strings.<locale>.js` (español necesita
  `'miles de millones'`/`'billones'` como parches cada 3 cifras; inglés tiene
  una palabra por grupo: `thousand/million/billion/trillion`). `tools/numbers/`
  de Calculia (ahora una app separada de la suite) es un ejemplo
  funcionando de este patrón si hace falta migrarlo de vuelta.
- **Horas**: "y cuarto"/"menos cuarto"/"y media" no son "and a quarter"/"less a
  quarter" en inglés natural — son "quarter past"/"quarter to"/"half past".
  Cualquier actividad que lea un reloj en voz alta necesita una pequeña tabla
  de frases `es`/`en` para estas expresiones fijas, no una traducción palabra
  por palabra. `tools/clock/` de Calculia (ahora una app separada de la
  suite) es un ejemplo funcionando de este patrón si hace falta migrarlo
  de vuelta.

**Regla general**: antes de traducir literalmente un texto con un número, una fecha,
una hora o una moneda, comprobar cómo lo diría de verdad un hablante nativo del
idioma destino. Si hace falta, la plantilla puede tener una estructura de frase
distinta por idioma (ver `precioConCentimos`, con `'{euros} y {c} céntimos'` en
español vs. `'{euros} and {c} cents'` en inglés — mismo orden aquí, pero no hay que
asumirlo).

## 3. Contenido cultural (dichos, chistes, adivinanzas, nombres): NO traducir literalmente

Regla igual de estricta que la del §2, pero para texto en vez de números: **un dicho,
un chiste o una adivinanza traducidos palabra por palabra del español dejan de
funcionar en inglés** — el chiste ya no da risa, el dicho no existe como tal, la
adivinanza pierde la rima o el doble sentido en el que se apoyaba. La versión en
cada idioma tiene que ser un contenido **propio de ese idioma**, con la misma
dificultad e intención pedagógica que el original, no una traducción de él.

- **`tools/idioms/`**: los dichos en inglés son modismos ingleses reales
  ("Break the ice", "Piece of cake", "Once in a blue moon"), no la traducción de
  "A quien madruga, Dios le ayuda".
- **`tools/comedy-club/`**: los chistes en inglés son juegos de palabras que
  funcionan en inglés ("Why did the bicycle fall over? Because it was two-tired.").
- **`tools/sentence/`**: los nombres de los personajes son nombres propios del idioma
  (`Emma`, `Jack`, `Grace`, `Grandma`), no los nombres españoles.
- **`tools/categories/`, `tools/vocabulary/`, `tools/whats-missing/`, etc.** (vocabulario
  de objetos cotidianos): aquí sí corresponde la traducción directa palabra a
  palabra (`Perro` → `Dog`).

## 4. Puntos con lógica binaria `es`/`en` (a generalizar al añadir un idioma)

Grep de referencia: `grep -rn "locale() === 'en'" assets/ tools/`.

| Archivo:línea | Qué hace | Qué hay que cambiar para un 3er idioma |
|---|---|---|
| `assets/js/i18n.js:17` (`SOPORTADOS`) | `var SOPORTADOS = ['es', 'en'];` | Añadir el código de idioma: `['es', 'en', 'fr']` |
| `assets/js/i18n.js:87` (`lang()`) | `return locale() === 'en' ? 'en-US' : 'es-ES';` | Convertir en un mapa `{es:'es-ES', en:'en-US', fr:'fr-FR'}` con fallback |
| `assets/js/dinero.js:83` (separador decimal) | `App.i18n.locale() === 'en' ? '.' : ','` | Mapa por idioma |
| `site/index.html` (botones) + `pintarSelectorIdioma()` | 2 botones fijos | Añadir un tercer `<button>` + entrada en `pintarSelectorIdioma()` + listener |

## 5. Receta: añadir un idioma nuevo (ejemplo: francés, `fr`)

Ejecutar en este orden. Cada paso es mecánico salvo el 4 (contenido) y el 5 (números/horas).

### Paso 1 — Registrar el idioma en el núcleo

En `assets/js/i18n.js`:

```js
var SOPORTADOS = ['es', 'en', 'fr'];
```

Añadir `fr` al diccionario `core`/`feedback`:

```js
fr: {
  core: {
    back: '← Retour', backToMenu: 'Retour au menu', playAgain: 'Rejouer',
    next: 'Suivant →', listen: '🔊 Écouter',
    listenInstructions: 'Écouter les instructions', listenText: 'Écouter le texte',
    loading: 'Chargement…', roundComplete: 'Manche terminée !'
  },
  feedback: {
    success: ['Bravo !', 'Génial !', "Tu l'as fait !"],
    encourage: ['Presque. Essaie encore !', 'Pas grave. Encore une fois !']
  }
}
```

Generalizar `lang()` (hoy binario, ver §4):

```js
var BCP47 = { es: 'es-ES', en: 'en-US', fr: 'fr-FR' };
function lang() { return BCP47[locale()] || BCP47[POR_DEFECTO]; }
```

### Paso 2 — Selector de idioma en la landing

En `site/index.html`, añadir un tercer botón dentro de `.idioma-selector`:

```html
<button type="button" class="btn-idioma" id="btnIdiomaFr" data-locale="fr" aria-pressed="false">🇫🇷 Français</button>
```

y en el `<script>` de la misma página: añadir su línea en `pintarSelectorIdioma()`
y su `addEventListener('click', () => App.i18n.setLocale('fr'))`.

### Paso 3 — Landing: `site/strings.fr.js`

Crear el archivo `strings.fr.js` con las mismas claves que `strings.es.js` / `strings.en.js`:

```js
(function () {
  'use strict';
  App.i18n.register({
    title: 'Routime',
    saludo: '...',
    // ... resto de claves traducidas al francés
  }, 'fr');
})();
```

### Paso 4 — Crear `strings.fr.js` por cada actividad (66 archivos)

Por cada `tools/<slug>/strings.es.js` y `tools/<slug>/strings.en.js`, crear el
equivalente `strings.fr.js` con las **mismas claves** (mismos nombres, misma
estructura anidada). El script de validación de paridad del Paso 7 lo verificará.

Este paso es el más tedioso. Considerar automatizarlo en el futuro con un script de
generación basado en `strings.es.js`.

### Paso 5 — Formato específico del francés (números, horas, dinero)

No basta con traducir palabra por palabra (ver §2):

- **Números**: el francés también usa escala larga como el español (10⁹ = "milliard").
  Comprobar `DATA.lecturas` con cuidado.
- **Separadores**: francés usa espacio fino para miles y `,` para decimales.
- **Horas**: "trois heures et quart" / "moins le quart" / "et demie" — escribir las
  claves pensando en cómo lo diría un hablante nativo.

### Paso 6 — Actualizar `sw.js` y `scripts/check.js`

Subir `VERSION` en `sw.js` y añadir `strings.fr.js` por actividad al array
`ARCHIVOS`. La regex de `scripts/check.js` (check #3) acepta cualquier locale
configurado en `STRING_LOCALES`; basta con añadir `'fr'` al inicio de ese array.

### Paso 7 — Verificar paridad de claves

`scripts/check.js` ya valida que `strings.es.js`, `strings.en.js` (y cualquier
otro `strings.<locale>.js`) tengan **exactamente las mismas claves**. Si añades
`fr`, actualiza `STRING_LOCALES` en `scripts/check.js` para incluir `'fr'`:

```js
var STRING_LOCALES = ['es', 'en', 'fr'];
```

Y ejecuta:

```bash
node scripts/check.js
```

Si alguna clave falta en `fr`, `check.js` lo listará con detalle ("solo en es",
"solo en en").

### Paso 8 — Verificación funcional

- Landing: el tercer botón cambia todo el sitio y persiste en
  `localStorage['routime:locale']`.
- Cada herramienta carga sin errores de consola en el idioma nuevo.
- `numeros` y `reloj` en particular: leer en voz alta un par de preguntas y
  comprobar que el número/hora es correcto.

## 6. Qué NO hacer

- No dar por buena una traducción automática de números, fechas, horas o dinero sin
  comprobar la convención real del idioma (§2 y Paso 5).
- No dejar una clave sin su equivalente en todos los idiomas soportados — el
  fallback a español oculta el hueco en vez de fallar de forma visible.
- No usar arrays en `strings.<locale>.js` para datos indexados por posición/número (`t()` los
  aplana con `join(', ')`); usar un objeto con claves de texto (`{0:'', 1:'...'}`).
- No añadir un idioma nuevo sin generalizar primero los puntos binarios `es`/`en`
  del §4 — si no, el idioma nuevo heredará en silencio el comportamiento inglés (o
  español) en formato de números/horas.
- No traducir literalmente dichos, chistes, adivinanzas o cualquier texto que
  dependa de un juego de palabras, una rima o una referencia cultural — escribir
  contenido propio del idioma destino con la misma dificultad e intención (§3).
- **No borrar los archivos monolíticos `strings.js` sin actualizar `sw.js`**:
  el service worker cachea los archivos listados en `ARCHIVOS`. Tras el
  refactor multi-archivo, `strings.<locale>.js` reemplazan a `strings.js`
  (subimos `VERSION` para forzar redownload).

---

## 7. Resumen histórico

- **v3.x (legacy)**: un único `strings.js` por actividad con `{es: {...}, en: {...}}`.
  Simple, pero mezclaba idiomas en cada archivo y descargaba ambos al cliente.
- **v4+**: sistema multi-archivo con `strings.<locale>.js`, carga condicional
  desde `index.html` con `document.write` síncrono. Mantiene retrocompatibilidad
  con la firma legacy de `register(dict)` para transiciones suaves.
- **Migración**: ejecutar `node scripts/refactor-i18n.js` desde la raíz del repo
  convierte automáticamente todos los `strings.js` a `strings.es.js` +
  `strings.en.js`, actualiza el `index.html` correspondiente y borra el
  monolítico. Respaldado por `--dry-run` para simular sin tocar archivos.
